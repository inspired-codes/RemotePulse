🛡️ Security & Trust Architecture

Why the relay can’t hijack
your connection.

RemotePulse lets your phone run scripts on your computers through an internet relay — without trusting that relay with your commands, your results, or your keys. Here is what that means in plain English, followed by the exact cryptography and our honest limits.

“If anyone swaps a key on the way, pairing fails.”
📖 Open Source on GitHub (AGPL-3.0) 🔏 Attested Worker Releases ✅ Verify a Download Yourself

The Short Version

Four guarantees that protect your business PCs and servers, without needing a cryptography degree.

📱 Only your phone can trigger a script

Every command is locked and signed on your phone before it ever leaves your browser. The relay (our Hub) cannot invent or alter a command — your computer checks your phone’s signature and throws away anything else. (One honest exception: see Honest Limits.)

🙈 The relay server is completely blind

Our cloud relay only passes scrambled packages between your phone and your computer. It never holds your encryption keys, so it cannot read the scripts you send or the output your computer sends back.

🔗 Pairing locks both screens together

To connect a new computer, you scan a one-time QR code shown directly on that computer’s screen and verify a 6-digit safety code on both screens. Neither the network nor the relay can slip in a fake key — if anyone swaps a key on the way, pairing fails.

🧱 Zero open ports on your firewall

Your computer reaches out over standard HTTPS to check for work. You never open inbound router ports, set up port forwarding, or expose PowerShell to the public internet.

1. QR Fragment

Secret never hits HTTP logs

http://localhost:7923/ generates a 256-bit secret S and embeds it with the Worker’s SPKI SHA-256 fingerprint fp in the URL fragment (/pairing/v2#k=<S>&fp=<fp>&ts=…). Browsers never send fragments to servers.

2. Derived Pairing ID

Hub never sees S

Both sides derive pid = HKDF-SHA256(S, "RemotePulse/pairing/v2/id") and POST only pid to /api/pairing/v2. The Hub matches the two halves by pid without ever learning S.

3. Bidirectional Key Binding

Fail-closed on both devices

The App aborts locally unless SHA-256(WorkerKey) == fp. The Worker verifies AppBindTag (an HMAC-SHA256 under HKDF-SHA256(S, "RemotePulse/pairing/v2/bind") covering pid, fp, AppId, and AppPublicKey) in constant time.

4. Command & Replay Guard

Worker-side ExecutedCommandStore + Hub SeenNonces

Commands use hybrid ECDH P-256 + AES-256-GCM plus ECDSA P-256 signatures. The Hub rejects replayed request nonces via SeenNonces, and the Worker itself persists executed command IDs in ExecutedCommandStore and rejects envelopes older than 5 minutes — so even a malicious Hub cannot replay commands. Results return encrypted with a per-command 256-bit ReplyKey (AAD = CommandId).

🔍 Inspect Before You Run

You never have to run irm … | iex blindly. On the home page, you can read get-worker.ps1 (137 lines of plain PowerShell) or switch to the Manual (Zip) tab to download the Windows or Linux Worker zip directly.

Both this server’s /downloads/ folder and the GitHub Releases page serve the exact same Worker zips built on GitHub-hosted runners — never local workstation builds.

1. Verify GitHub Build Provenance (SLSA)

Every public Worker release is built by GitHub Actions from a tagged commit with a signed Sigstore/SLSA build-provenance attestation. Using the GitHub CLI (gh), you can verify a zip downloaded from either GitHub Releases or this server: 

gh attestation verify RemotePulse-Worker-windows-x64.zip \
  --repo inspired-codes/RemotePulse

For Linux, pass RemotePulse-Worker-linux-x64.zip. To pin the workflow and runner environment strictly, add --signer-workflow inspired-codes/RemotePulse/.github/workflows/release.yml --deny-self-hosted-runners.

2. Compare SHA-256 Against the GitHub Release

Compute the SHA-256 of the downloaded zip locally and compare it to the digest listed on GitHub Releases (and to this server’s worker-version.json): 

# Windows (PowerShell)
(Get-FileHash ./RemotePulse-Worker-windows-x64.zip -Algorithm SHA256).Hash

# Linux / macOS
sha256sum RemotePulse-Worker-linux-x64.zip

If even one byte of the zip differs from the attested Release artifact, both the SHA-256 check and gh attestation verify fail.

Honest Security Limits

Trust comes from stating exact boundaries, not marketing absolutes.

✅ What a compromised Hub cannot do

  • Cannot read scripts or output: The Hub database stores only ciphertext and public keys.
  • Cannot run commands on paired PCs: The Worker rejects any command not signed by your phone’s private key.
  • Cannot silently swap keys during Pairing v2: Any substitution breaks fp on the phone, breaks AppBindTag on the PC, and mismatches the 6-digit safety code.

⚠️ What you still trust today

  • Code delivery from the same host: The same server delivers the Web App (/app) and the Worker downloads (/downloads/*, get-worker.ps1). You can now verify any Worker zip yourself via gh attestation verify and GitHub Release hashes — but the Worker and installer do not enforce attestations or offline signatures automatically yet, and the Web App (PWA) and Hub container images are not attested yet.
  • What build attestations do (and don’t) prove: An attestation proves which public workflow built a Worker zip from which commit. It does not by itself prove the code is bug-free or benign — reading the open-source repository is what lets you audit it.
  • Physical QR visibility: Anyone who can see or photograph your PC’s http://localhost:7923/ screen during pairing holds the QR secret.
  • Pre-2.0.0 pairings: Machines paired before v2.0.0 stay on legacy TOFU pairing until you unpair and re-pair them.
  • Hub metadata: The Hub sees which AppId talks to which MachineId, when, payload sizes, and connection IP addresses (used for rate limiting, and included in support reports) — never script or output contents.
What’s done & what’s next: The source repository (inspired-codes/RemotePulse) is now public, and every Worker release carries a signed GitHub build-provenance attestation served verbatim by this host. Next on the roadmap: signed Worker updates verified automatically against an offline release key (so the Worker itself checks authenticity on every update), plus a clean self-hosting bundle.

Threat Model FAQ

Direct answers to the hard questions skeptics ask first.

What happens if the RemotePulse Hub server or database is hacked?
An attacker who dumps the Hub database gets encrypted payloads, public keys, machine IDs, and timing/size metadata. They cannot decrypt past or future scripts or command outputs, and they cannot send commands to an already-paired PC because your Worker requires your phone’s ECDSA P-256 signature. Since v2.0.0, even a Hub compromised while you pair cannot swap keys. The remaining limit is software delivery: the same host serves the Web App and Worker downloads — you can verify any Worker zip against GitHub’s signed build attestation before installing it, while Web App (PWA) delivery and automatic update-signature checks are not yet enforced.
How does Pairing v2 stop a Man-in-the-Middle attack?
Your PC shows a QR code on http://localhost:7923/ carrying a one-time 256-bit secret S and the SHA-256 fingerprint fp of your PC’s public key. S never leaves the two devices — both sides only send a derived pairing ID pid to the Hub. Your phone rejects any PC key that does not match fp, your PC rejects any phone key without a valid AppBindTag HMAC tied to S, and both screens display the same 6-digit safety code. Protect the QR screen itself while pairing, and re-pair any machine originally paired before v2.0.0.
Where are my private keys stored?
On your phone, private keys live inside your browser’s sandboxed IndexedDB/WebCrypto store and are never transmitted over the network. On your PC, the Worker key lives in client_key.dat protected by OS permissions: mode 0600 inside a 0700 /var/lib/remotepulse directory on Linux, or an inheritance-free NTFS ACL restricted to SYSTEM (and local Administrators) under %ProgramData%\RemotePulse on Windows.
Can someone replay an old command they captured on the wire?
No. The Hub rejects replayed HTTP request nonces via SeenNonces (recorded after signature verification) and enforces a 5-minute clock-skew window. More importantly, the Worker itself enforces replay protection via ExecutedCommandStore: it rejects command envelopes older than 5 minutes and persists every executed command ID across restarts, so even a malicious Hub cannot replay an old command.
Do I need to open any router or firewall ports?
Zero. The Worker opens outbound HTTPS long-poll connections to the Hub. Only local loopback access (http://localhost:7923/) is used on the machine itself for pairing and local status.
